## core/services

#### `camera_service.dart`
`CameraService` — wraps the `camera` plugin, single shared `CameraController` for preview/stream/capture (merged from a two-controller design in an earlier session; see `LIMITATIONS_AND_ROADMAP.md` §1 for the still-open device-verification of that merge).

**Rewritten this (sixteenth) session — resolution, focus, and zoom.** `ResolutionPreset` is now a `CameraQuality` enum (`balanced` → `high`/720p, `sharp` → `veryHigh`/1080p, default `sharp`) instead of the hardcoded `ResolutionPreset.medium` this file actually shipped with despite the prior entry describing `.high` — 480p was upscaling on-screen and being written to every saved still. `setQuality()` swaps it at runtime, recreating the controller (caller must restart the image stream after). Zoom state (`currentZoom`/`setZoom()`) and tap-to-focus (`focusAndMeterAt(Offset normalized)`, sensor-normalized 0..1 coordinates) both moved into this service from `camera_screen.dart`, since only the service survives a lens flip or resume — the old screen-owned `_currentZoom` went stale across `switchLens()` and snapped to a large digital zoom on the next pinch. `focusAndMeterAt` locks focus/exposure at the tapped point for 3s (`_refocusToContinuousDelay`) then returns to `FocusMode.auto`/`ExposureMode.auto`, which `_createController` now also sets explicitly on every (re)creation rather than relying on the plugin's default. `capture()` inserts a 150ms settle delay (`_preCaptureSettleDelay`, untuned guess) between stopping the image stream and firing the shutter, to let continuous AF reconverge after the surface set changes. Debug-only `camera_config:`/`camera_config: still written...` logging added to confirm the negotiated `previewSize` and saved-still dimensions actually match the requested preset — a preset is a request, not a guarantee, and the prior `.medium` bug went unnoticed for this reason.

**Not yet device-verified**, and now a more pointed ask than before the resolution change: continuous AF behavior on `LIMITED`-hardware devices, whether `veryHigh` measurably slows ML Kit frame processing on lower-end hardware (drop to `.balanced` if so), and whether the 150ms pre-capture delay is doing anything at 0ms A/B. See `LIMITATIONS_AND_ROADMAP.md` §1.

#### `ml_kit_service.dart`
`MlKitService` — owns the live-frame `PoseDetector`, `FaceDetector`, `SelfieSegmenter`, converts a `CameraImage` to ML Kit's `InputImage`, runs all three detectors sequentially per frame behind a `_busy` guard, broadcasting `MlKitAnalysisResult` on `analysisStream`. The live `FaceDetectorOptions` actually has `enableClassification: false` (this entry previously said `true` — that was wrong; see the `enableClassification` product-decision item in `LIMITATIONS_AND_ROADMAP.md`). `processImage` wraps the three detector calls in a `try`/`catch` — a failure is reported via `ErrorReportingService` and counted; after 5 consecutive failures (`_maxConsecutiveFailuresBeforeFlagging`) the service emits `true` on `unavailableStream`, and `false` again the next time a frame succeeds. `SelfieSegmenter` here runs with `enableRawSizeMask: true` — deliberately kept for the live-stream path (per-frame performance reasons), unlike `reference_image_analyzer.dart`'s one-shot detector, which had the same flag removed after it caused a mask/image size mismatch there. Not yet confirmed whether the live-stream mask's aspect ratio always matches the (fixed-resolution) camera frame in practice — see `LIMITATIONS_AND_ROADMAP.md`.

**Rewritten this session (bug fix):** `processImage(image, description, deviceOrientation)`'s third parameter changed from a pre-computed `InputImageRotation` to a raw `DeviceOrientation`. Previously the caller (`camera_screen.dart`) computed rotation itself with a formula that ignored device orientation and didn't match either camera's correct rotation-compensation convention; `description` was accepted here but never actually used. Now `rotationFor(description, deviceOrientation)` computes rotation internally, applying the front-camera formula (`sensorOrientation + deviceRotation`) or back-camera formula (`sensorOrientation - deviceRotation`, both mod 360) based on `description.lensDirection` — the two conventions differ and using the wrong one for front camera was the root cause of `shoulderAngle`/`faceAngle` reading `FAIL` regardless of actual pose. Not yet re-confirmed on a physical device after the fix — see `LIMITATIONS_AND_ROADMAP.md` §1.

#### `tracking_engine.dart`
`TrackingEngine` — constructed with a `DetectionThresholds thresholds` (default `DetectionThresholds.defaultValues`). `smoothScene` unchanged. `trackingProgress()` guards both `eyesOpen` and `expression` on *both sides non-null* before adding them to the weighted average, so they cleanly drop out now that they're permanently `null` — this behavior was already correct and is locked in by test. **First reviewed this (fifteenth) session** — never in front of any prior session despite being central to auto-capture behavior.

**Bug found and fixed this (seventeenth) session — no `reset()` existed at all.** The nine-plus-nineteen debounce-streak/pending-value fields across `smoothSubject()`/`smoothScene()` are provider-scoped singleton state, same class of bug as `pose_analyzer.dart`/`face_analyzer.dart`'s stabilizers before their sixteenth-session `reset()` additions — but this file had no equivalent. More importantly: `smoothSubject()`/`smoothScene()`'s EMA blends each new frame against whatever `subjectProfileProvider`/`sceneProfileProvider` currently hold, so `resetLiveAnalyzers()`'s existing fix (resetting only the two analyzers) left the first post-flip frame still averaging against the stale pre-flip profile — the actual source of "previous" here is the provider state, not anything internal to this class. Added `reset()` (clears all 19 fields); `scene_providers.dart`'s `resetLiveAnalyzers()` now calls it and additionally resets both providers to their defaults — see that entry.

**Bug found and fixed — `faceAngleDegrees`'s score block used linear `ComparisonMath.deviation()`, not circular.** Fourth confirmed recurrence of the bug class first found in the tenth session for `shoulderAngleDegrees` (which this file already handled correctly via `circularDeviation` — only the `faceAngleDegrees` block had the bug). Fixed to match.

**Change — `bodyYawEstimate` added to `trackingProgress()`'s scoring, for the first time.** Previously not scored at all, target-null or not — a real gap, distinct from (and the actual reason `scene_providers.dart`'s `targetSubjectProfileProvider` fix from earlier the same session had no effect on) the reported symptom of auto-capture firing too easily. Uses `circularDeviation`, mirroring `shoulderAngleDegrees`'s existing treatment. **`shoulderBalanceRatio`/`shoulderSpanRatio` deliberately not added this session** — both are ratios, not angles, and this session didn't have `comparison_math.dart` to confirm the right threshold function; reusing the degree-calibrated `thresholdForPose` for a 0–1-range ratio would make the check trivially always pass. **Addendum (outside the normal per-session log):** both have since been added, each its own scoring block (relative deviation, `thresholdForPoseRatio()`/`maxDeviationForPoseRatio`, same null-handling shape as the existing `bodyRatio` block) — `comparison_math.dart` needed no changes, since the ratio-calibrated functions already existed. Not yet device-verified.

**Root cause of "auto-capture fires on far less than a full pose match," fully explained here.** `trackingProgress()`'s scoring loop only adds a criterion to the averaged `scores` list when `target.X != null` — a `null` target (the reference photo's own `bodyRatio` came back `null` because its knees/ankles were outside the analyzed frame) silently drops that criterion from the average entirely, rather than counting against the match or being handled as a special case. Combined with `bodyYawEstimate`/`shoulderBalanceRatio` never being scored at all (see above), a real session could reach `trackingProgress = 1.000` while only `shoulderAngle` and `brightness` had anything real to compare against. Not changed this session — this is describing the mechanism, which is now understood, not a bug in the null-skip design itself (a genuinely-missing reference measurement arguably *should* be excluded from the average, since there's nothing to compare) so much as a consequence of how much data the specific reference photo used to diagnose this had.

**Two bugs found and fixed this (thirteenth) session, `smoothSubject()` only:**
1. `shoulderAngleDegrees`/`faceAngleXDegrees`/`faceAngleZDegrees`/`bodyYawEstimate` are all circular quantities (wrap at ±180°) but were smoothed with the plain linear `_ema` helper used for every other field. Added `_circularEma` (cos/sin-decomposition averaging, same idea as `ComparisonMath.circularDeviation`) and switched all four fields to it.
2. `smoothSubject()`'s return statement omitted `shoulderBalanceRatio`/`shoulderSpanRatio`/`bodyYawEstimate` entirely from the `SubjectProfile` it builds — the same failure mode as the fourth-session "dropped fields" bug (see the top-of-file note), recurring for three fields added in later sessions. Added missing-streak tracking and smoothing for all three, and included them in the return. Also now passes through `raw.metricConfidence` unsmoothed (audit migration step 8 — see `subject_profile.dart`).

**Bug found and fixed (tenth session):** `trackingProgress()`'s shoulder-angle score used `ComparisonMath.deviation()` (plain linear absolute difference) on `shoulderAngleDegrees`, a circular quantity (`atan2` output, range -180°..180°). When the live subject's and reference's angles fell on opposite sides of the ±180° wraparound point, deviation computed as ~300–340° instead of the true small difference, tanking this one attribute's `similarity` score toward 0 and dragging the whole averaged `trackingProgress` value below `minTrackingProgressForCapture` regardless of every other attribute being fine — the root cause of auto-capture rarely/never firing. Fixed to use `ComparisonMath.circularDeviation(...,360.0)`, matching the identical fix applied to `reference_comparison_engine.dart`'s `_evaluateShoulderAngle` — see `README.md` §11 for the full account.

#### `sherpa_tts_service.dart`
`SherpaTtsService` — wraps `sherpa_onnx.OfflineTts` (VITS/Piper engine). `init()` extracts the bundled VITS model's asset files (`assets/models/vits-en/`: `model.onnx`, `tokens.txt`, `espeak-ng-data/`) to a writable app-support directory on first run. `speak(phrase, {emphasis})` maps `TtsEmphasis` to `speed`/`silenceScale` via `generateWithConfig()`, writes via `sherpa_onnx.writeWave()` to a temp WAV, plays via `audioplayers`' `AudioPlayer.play(DeviceFileSource(...))`.

**Bug found and fixed this (fifteenth) session — `_ensureModelExtracted()` was silently broken since the seventh session by a Flutter SDK breaking change.** It read the asset manifest via `rootBundle.loadString('AssetManifest.json')` + `json.decode(...)` — a pattern that worked when this file was first written, but Flutter's tooling stopped generating `AssetManifest.json` in a subsequent stable release (confirmed against Flutter's own published breaking-change doc), so every `init()` call had been throwing `Unable to load asset: "AssetManifest.json"` on a real device the whole time, silently swallowed by a bare `catch` one layer up in `app_tts_service.dart` (see that entry) — which is why this had never shown up as a failure in any prior session's log review; the fallback to `flutter_tts` just quietly worked instead. Fixed per Flutter's own documented migration path: `AssetManifest.loadFromAssetBundle(rootBundle)` + `.listAssets()`, replacing the manual JSON parse; `dart:convert` import dropped (no longer used anywhere in this file).

**Two more changes this session, once the asset bug above was fixed and playback itself needed hardening.** (1) **`initFuture`, a new public field** — `init()`'s `Future` is now stored on the instance (set by `sherpaTtsServiceProvider` right after construction) so any external caller (now `splash_screen.dart` — see that entry) can `await` initialization completing, instead of only being able to poll `isReady`. (2) **`speak()`'s wait for `audioplayers` playback completion now has a 15-second timeout** — previously `await completer.future;` had no timeout at all, meaning a hang here (player never firing `onPlayerComplete`/a terminal `onPlayerStateChanged`) would wedge `AppTtsService`'s serial speech queue permanently, since every subsequent `speak()` call queues behind an in-flight one. Subscription cleanup (`completeSub`/`stateSub`) moved into a `finally` block so it runs on the timeout/error path too, not just the success path as before.

#### `app_tts_service.dart`
`AppTtsService` — thin wrapper exposing `speak(phrase, {emphasis})`/`stop()`. Tries `SherpaTtsService` first (if `isReady`); falls back to `TtsService` (flutter_tts) on any thrown error or when the sherpa model isn't ready yet.

**Bug found and fixed this (fifteenth) session — `_speakNow()` had a bare `catch (_) {}` around `sherpa.speak(...)`, silently discarding the real exception and falling through to `flutter_tts` with zero trace.** This is the exact M6 bare-catch pattern fixed everywhere else in this codebase in the thirteenth session — present here the whole time because this file wasn't part of that pass, and the direct cause of the `AssetManifest.json` bug (see `sherpa_tts_service.dart`'s entry) staying invisible across every prior session that touched TTS. Fixed: now logs the caught exception and stack trace before falling back, plus a new log line for `sherpa.isReady`'s value at the top of every call, so a future failure is visible on first read of the log instead of requiring a bare-catch hunt first.

**`speak()` gained a new `interrupt` parameter this (nineteenth) session — `force: true` alone never actually interrupted anything.** `force` only bypasses the "don't repeat the identical phrase" dedup check inside `SherpaTtsService`/`TtsService`; it has no effect on this class's own `_queue` (a strict `Future`-chain), so a call with `force: true` still waited for whatever was already queued/mid-playback to finish first. Traced from `capture_providers.dart`'s "Hold still." call — since `cameraService.capture()` runs only after that `speak()` call resolves, the actual shutter could fire several seconds after the pose that triggered capture, once a long coaching sentence happened to still be playing. `interrupt: true` now calls `stop()` (killing current playback, which unblocks whatever `speak()` call was mid-`await` inside `SherpaTtsService`/`TtsService` via their own player-state listeners) and resets `_queue = Future.value()` before building the new chain, so the phrase cuts in immediately instead of waiting in line. Both call sites in `capture_providers.dart` (`holdStillPhrase`, `sessionCompletePhrase`) updated to pass it alongside the existing `force: true`. **Not device-verified:** whether interrupting `sherpa_onnx` mid-generation this way is glitch-free (vs. e.g. an audible artifact from the cut-off phrase) hasn't been confirmed on a physical device, and isn't covered by `full_pipeline_test.dart` either — see that entry's own scope note (native plugin dependencies, same reasoning as `MlKitService`/`CameraService` being out of scope there).

## core/analysis *(new, sixteenth session)*

#### `analysis_constants.dart` *(new)*
Shared sampling/scoring constants pulled out this session to fix a mismatch between the live and reference-photo background-clutter signals — previously each side sampled at its own fixed pixel step and both fed the result through the same `/12.0` divisor, comparing luma-gradient variance measured at two different spatial scales. `clutterStep(width)`/`adaptiveStep(width, height, targetSamples)` both return a step size that keeps sample count roughly constant regardless of source resolution — `light_analyzer.dart`'s live frames (720-1920px) and `reference_image_analyzer.dart`'s reference photos (often 3000+px) now sample at the same effective density. `clutterScoreFromVariance`/`normalizeClutterCount` centralize the `/12.0` variance divisor, the `0..10` score ceiling, and the `/10` normalization that `reference_comparison_engine.dart` and `score_calculator.dart` each had as an unexplained inline magic number. `kBrightnessTargetSamples = 2000` matches `light_analyzer.dart`'s pre-existing `_estimateBrightness` sampling density; `kMaskSampleStep = 4` matches its `_analyzeMask`. `DetectionThresholds.defaultBackgroundClutterThreshold` was tuned against the old, mismatched signal and needs a fresh pass now that both sides agree — see `LIMITATIONS_AND_ROADMAP.md` §1.

- `original == null` → `.recover` if the crop detector observed it in-frame with likelihood ≥ `kMinLandmarkLikelihood`, else `.absent`.
- `original != null` → `.reject` only when mask confidence at the *original* landmark's own coordinates is below `kContradictionMaskConfidenceCeiling` (0.1) **and** the crop detector either didn't observe it (likelihood below `kContradictionCropLikelihoodCeiling`, 0.3) or placed it outside the crop's own bounds (checked in crop-local coordinates, before the shift back into original-image space) — two independent signals required to agree, so a merely-weak crop re-detection alone can't override a landmark the original pass and the mask both still support. - Otherwise `.keep`, using the original detector's own `RawLandmark`.

The final `verified` map (kept + recovered landmarks only; rejected/absent landmarks simply never enter it) is run back through `PoseLandmarkGate.fromRawLandmarks` and a fresh `sampleMaskTrust` pass, same as the eleventh session's merge step. `changedAnyLandmark` is now `true` whenever any landmark was recovered or rejected (previously only tracked confirmed recoveries).
