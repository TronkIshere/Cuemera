## core/services

#### `camera_service.dart`
`CameraService` — wraps the `camera` plugin. **Merged this session from a two-`CameraController` design into one.** Previously maintained `_controller` (medium-res, live ML-analysis stream) and `_previewController` (high-res, on-screen preview) as two independently-opened sessions against the same camera lens — this is not how CameraX (the `camera` plugin's Android backend) is meant to be driven; it already supports Preview + ImageAnalysis + ImageCapture as one bound session, and running two separate sessions instead left CameraX negotiating a degraded configuration on devices reporting a `LIMITED` Camera2 hardware level (confirmed on an Oppo Reno 14/ColorOS device: preview/capture were visibly softer than the stock camera app, autofocus did not behave like continuous AF). Now there is a single `_controller` (`ResolutionPreset.high` — the old preview/capture preset) driving preview, `startImageStream()`, and `capture()` alike; `previewController`/`isPreviewInitialized`/`initPreviewController()` are gone. `capture()` no longer spins up any third, temporary controller either (that per-photo lifecycle was already replaced by directly reusing the (then-)preview controller in a prior session) — it now stops the shared controller's image stream before `takePicture()` and resumes it afterward via a `try`/`finally`, using the `onImage` callback `CameraService` retains internally from the last `startImageStream()` call, so the caller doesn't need to re-supply it after every capture. `lastCaptureControllerSetupLatency`/`lastCaptureControllerTeardownLatency` stay `Duration.zero` — there's no separate controller lifecycle left to time at all now, not just "no longer a separate per-photo controller" as before. `lastCaptureShutterLatency` (measuring `takePicture()` itself) and `lastGallerySaveSucceeded` tracking unchanged. `switchLens()` now creates one controller instead of two; `pauseCameras()`/`resumeCameras()`/`dispose()` similarly collapsed to one dispose/recreate path. **Not yet device-verified** — see `LIMITATIONS_AND_ROADMAP.md`.

#### `memory_service.dart`
`MemoryService` — thin wrapper over two Hive `Box`es (`shooting_habits`, `album_state`) with generic get/set. `memoryServiceProvider` is a `FutureProvider<MemoryService>` that awaits `init()` before resolving. **New this session:** the habits box now also stores the AI-coaching-toggle flag (`ai_coaching_enabled`, via the existing generic `getHabit`/`setHabit`) — no new methods needed, the service itself is unchanged. Schema versioning for the data it stores continues to live in the consumer (`album_providers.dart`), not in this generic service.

#### `ml_kit_service.dart`
`MlKitService` — owns the live-frame `PoseDetector`, `FaceDetector`, `SelfieSegmenter`, converts a `CameraImage` to ML Kit's `InputImage`, runs all three detectors sequentially per frame behind a `_busy` guard, broadcasting `MlKitAnalysisResult` on `analysisStream`. The live `FaceDetectorOptions` actually has `enableClassification: false` (this entry previously said `true` — that was wrong; see the `enableClassification` product-decision item in `LIMITATIONS_AND_ROADMAP.md`). `processImage` wraps the three detector calls in a `try`/`catch` — a failure is reported via `ErrorReportingService` and counted; after 5 consecutive failures (`_maxConsecutiveFailuresBeforeFlagging`) the service emits `true` on `unavailableStream`, and `false` again the next time a frame succeeds. `SelfieSegmenter` here runs with `enableRawSizeMask: true` — deliberately kept for the live-stream path (per-frame performance reasons), unlike `reference_image_analyzer.dart`'s one-shot detector, which had the same flag removed after it caused a mask/image size mismatch there. Not yet confirmed whether the live-stream mask's aspect ratio always matches the (fixed-resolution) camera frame in practice — see `LIMITATIONS_AND_ROADMAP.md`.

**Rewritten this session (bug fix):** `processImage(image, description, deviceOrientation)`'s third parameter changed from a pre-computed `InputImageRotation` to a raw `DeviceOrientation`. Previously the caller (`camera_screen.dart`) computed rotation itself with a formula that ignored device orientation and didn't match either camera's correct rotation-compensation convention; `description` was accepted here but never actually used. Now `rotationFor(description, deviceOrientation)` computes rotation internally, applying the front-camera formula (`sensorOrientation + deviceRotation`) or back-camera formula (`sensorOrientation - deviceRotation`, both mod 360) based on `description.lensDirection` — the two conventions differ and using the wrong one for front camera was the root cause of `shoulderAngle`/`faceAngle` reading `FAIL` regardless of actual pose. Not yet re-confirmed on a physical device after the fix — see `LIMITATIONS_AND_ROADMAP.md` §1.

#### `theme_preference_service.dart`
`ThemePreferenceService extends StateNotifier<ThemeMode>` — persists dark/light via `shared_preferences`. Unchanged.

#### `tracking_engine.dart`
`TrackingEngine` — constructed with a `DetectionThresholds thresholds` (default `DetectionThresholds.defaultValues`). `smoothScene` unchanged. `trackingProgress()` guards both `eyesOpen` and `expression` on *both sides non-null* before adding them to the weighted average, so they cleanly drop out now that they're permanently `null` — this behavior was already correct and is locked in by test.

**Two bugs found and fixed this (thirteenth) session, `smoothSubject()` only:**
1. `shoulderAngleDegrees`/`faceAngleXDegrees`/`faceAngleZDegrees`/`bodyYawEstimate` are all circular quantities (wrap at ±180°) but were smoothed with the plain linear `_ema` helper used for every other field. Added `_circularEma` (cos/sin-decomposition averaging, same idea as `ComparisonMath.circularDeviation`) and switched all four fields to it.
2. `smoothSubject()`'s return statement omitted `shoulderBalanceRatio`/`shoulderSpanRatio`/`bodyYawEstimate` entirely from the `SubjectProfile` it builds — the same failure mode as the fourth-session "dropped fields" bug (see the top-of-file note), recurring for three fields added in later sessions. Added missing-streak tracking and smoothing for all three, and included them in the return. Also now passes through `raw.metricConfidence` unsmoothed (audit migration step 8 — see `subject_profile.dart`).

**Bug found and fixed (tenth session):** `trackingProgress()`'s shoulder-angle score used `ComparisonMath.deviation()` (plain linear absolute difference) on `shoulderAngleDegrees`, a circular quantity (`atan2` output, range -180°..180°). When the live subject's and reference's angles fell on opposite sides of the ±180° wraparound point, deviation computed as ~300–340° instead of the true small difference, tanking this one attribute's `similarity` score toward 0 and dragging the whole averaged `trackingProgress` value below `minTrackingProgressForCapture` regardless of every other attribute being fine — the root cause of auto-capture rarely/never firing. Fixed to use `ComparisonMath.circularDeviation(...,360.0)`, matching the identical fix applied to `reference_comparison_engine.dart`'s `_evaluateShoulderAngle` — see `README.md` §11 for the full account.

#### `tts_service.dart`
`TtsService` — wraps `flutter_tts`; `speak()` guards on `_ready` (set by `init()`) so calls before initialization silently no-op rather than throwing. `ttsServiceProvider` calls `service.init()` (fire-and-forget) on construction. File itself unchanged this (seventh) session, but its role changed: no longer called directly by feature code — it's now only reached as `AppTtsService`'s fallback (see below) when `sherpa_onnx` isn't ready or throws.

#### `sherpa_tts_service.dart` *(new, seventh session — in progress)*
`SherpaTtsService` — wraps `sherpa_onnx.OfflineTts` (VITS/Piper engine). `init()` extracts the bundled VITS model's asset files (expected under `assets/models/vits-en/`: `model.onnx`, `tokens.txt`, `espeak-ng-data/`) to a writable app-support directory on first run — reads `AssetManifest.json` and copies every file whose key starts with the configured prefix, since the native library needs real filesystem paths, not Flutter asset-bundle keys. `speak(phrase, {emphasis})` takes a `TtsEmphasis` (`mild`/`moderate`/`strong`) and maps it to both `speed` (1.0 → 0.88) and `OfflineTtsGenerationConfig.silenceScale` (0.2 → 0.45) via `generateWithConfig()`, plus appends a trailing `!` for `strong` — the practical ceiling of emphasis control this model exposes, since sherpa_onnx has no true prosody/SSML parameter. Output is written via the top-level `sherpa_onnx.writeWave()` (not a method on `GeneratedAudio` — an earlier draft assumed `audio.save()`, which doesn't exist in the Dart API and was a real compile error) to a temp WAV file, played via `audioplayers`' `AudioPlayer.play(DeviceFileSource(...))`. `OfflineTtsConfig`'s max-sentence-count field is named `maxNumSenetences` (that typo is genuinely in the shipped package, confirmed against multiple official sherpa-onnx examples — not a typo introduced here). **Not yet device-tested** — see `LIMITATIONS_AND_ROADMAP.md` §1.

#### `app_tts_service.dart` *(new, seventh session)*
`AppTtsService` — thin wrapper exposing `speak(phrase, {emphasis})`/`stop()`. Tries `SherpaTtsService` first (if `isReady`); falls back to `TtsService` (flutter_tts) on any thrown error or when the sherpa model isn't ready yet — mirrors the existing AI-coaching-phrase-or-fallback pattern already used for Gemma. Call sites (`voice_providers.dart`, `camera_screen.dart`) only depend on this provider, not on `SherpaTtsService`/`TtsService` directly, so the fallback logic stays in one place.

#### `expression_classifier.dart`
`classifyExpression({smilingProbability, leftEyeOpenProbability, rightEyeOpenProbability}) → String?` — the single shared expression classifier used by both `face_analyzer.dart` and `reference_image_analyzer.dart`. Unchanged — per the Signal Disable plan's non-goals, this file is gated off from the live path by `face_analyzer.dart`'s flag, not edited or deleted.

#### `error_reporting_service.dart`
`ErrorReportingService` (singleton via `ErrorReportingService.instance`) — centralized error/crash capture. `report(error, stackTrace, {context})` records an `ErrorReport` (capped at the 200 most recent, in memory only) and `debugPrint`s it; `reportFlutterError(FlutterErrorDetails)` adapts framework errors to the same call. Wired from `main.dart` (`FlutterError.onError`, `PlatformDispatcher.instance.onError`, `runZonedGuarded`) and called directly from every previously-silent `catch` in `reference_image_analyzer.dart`, `album_providers.dart`, `camera_service.dart` (gallery save), and `ml_kit_service.dart` (per-frame processing failures). **Thirteenth session (audit migration step 3/M6):** also now called from `coaching_phrase_model_service.dart` (`ensureInstalled()` logs then rethrows; `generate()` logs then returns `null`, unchanged external behavior), `ai_coaching_providers.dart`'s `_install()`, and `voice_providers.dart`'s generation call site (which distinguishes a `TimeoutException` from other failures via a separate `context` string). This file itself is unchanged — only its call sites grew. **Local-only** — a `TODO(remote-sink)` marks the intended extension point for a real service (Crashlytics/Sentry/custom backend) once one is chosen; reports do not currently survive app restart or leave the device.

## core/confidence

#### `confidence.dart`
`Confidence` value type (`[0,1]`, asserts range) + combination rules: `minOf` (a metric is only as trustworthy as its weakest input — used for cross-source combination, e.g. subject vs. reference), `productOf` (a landmark's confidence is the product of its independent signal components — one bad signal dominates), `decisionConfidence` (`= minOf([subject, reference])`). `ConfidenceFloors` — named thresholds (`eligibleToSpeak = 0.5`, `eligibleForLlmParaphrase = 0.7`, `referenceUsable = 0.4`) consumed by `coaching_eligibility.dart`. Already existed before the thirteenth session's audit migration work began, matched the audit's spec exactly, unchanged.

#### `reference_image_analyzer.dart`
`ReferenceImageAnalyzer.analyze(imagePath) → ReferenceProfile` — **pose trust changed this (eleventh) session:** `shoulderAngleDegrees`/`torsoScale`/`shoulderBalanceRatio`/`shoulderSpanRatio`/`bodyYawEstimate`/`bodyRatio` and `poseLandmarkPoints` (the drawn skeleton) are now all derived from one shared `PoseLandmarkGate` (`core/pose/landmark_gate.dart`, new — see its entry below) instead of separate per-field inline checks. `bodyRatio` keeps its own additional hip-to-ankle extrapolation guard (`_maxExtremityExtrapolationMultiplier = 4.0`) alongside the gate's knee-to-ankle segment budgets — the two catch different framings. The five independent analysis steps (pose, face, segmentation, decode, palette) still run concurrently via `Future.wait`; pose derivation itself (`_derivePose`) is now async, since Phase 2 crop-redetection (`reference_photo_crop_redetect.dart`, new — see below) is a second detection pass. Also added this session: `kDebugMode`-gated diagnostic logging (a cheap file-size+checksum fingerprint, plus a detection-outcome summary) on every `analyze()` call, to help confirm the still-unreproduced non-determinism report from the tenth session (see `LIMITATIONS_AND_ROADMAP.md`).

**Thirteenth session (audit migration step 8):** `_derivePose` now also computes `metricConfidence` for `ReferenceProfile` — a `Map<String, double>` keyed by field name (`shoulderAngleDegrees`/`shoulderBalanceRatio`/`bodyYawEstimate`/`shoulderSpanRatio`/`bodyRatio`), each the minimum `gate.trust(type)!.confidence.value` across that field's contributing landmarks (`Confidence.minOf`'s "as trustworthy as the weakest input" rule, applied manually here rather than importing `confidence.dart`'s helper — this analyzer already had its own local `minConfidence` closure for the equivalent purpose). Uses the already-Phase-2-reconciled `gate`, so this confidence reflects the crop-redetect veto, not just the first detection pass. Mirrors `pose_analyzer.dart`'s identical logic on the live side — kept as an independent implementation rather than a shared function, since this analyzer's `gate` has already been through reconciliation the live path never does.

**Pose trust changed again this (twelfth) session — pose detector switched to the accurate model.** `_detectPose`'s `PoseDetector` now constructs with `PoseDetectorOptions(model: PoseDetectionModel.accurate)` instead of the default `base` model. Reference-photo analysis runs once per image, not per frame, so the accuracy/latency trade-off costs effectively nothing here — deliberately not applied to the live-camera detector in `ml_kit_service.dart`, which stays on `base` to protect frame rate. Confirmed improvement via a real device log: a previously-false-`trusted` `rightKnee` correctly flipped to `suspect` under `accurate`, and two landmarks that had been permanently stuck `lowConfidence` even after crop-redetect were successfully recovered.

**Bug found and fixed this (tenth) session:** `shoulderAngleDegrees`/`torsoScale`/`shoulderBalanceRatio`/`bodyYawEstimate` were computed straight from `leftShoulder`/`rightShoulder` with **no** `likelihood` check at all — inconsistent with `bodyRatio` (above) and with `poseLandmarkPoints` (which does filter by `likelihood >= 0.6`). A shoulder landmark ML Kit itself flags low-confidence, and which the UI correctly declines to draw, could still silently drive the numeric shoulder-angle comparison used for coaching and auto-capture. #### `core/pose/landmark_gate.dart` *(new, eleventh session)*
`PoseLandmarkGate` — single source of pose-landmark trust, read by `reference_image_analyzer.dart`, `reference_picker_sheet.dart`, and `pose_analyzer.dart` (live) alike. #### `landmark_trust_classifier.dart` *(rewritten, eleventh session)*
`sampleMaskTrust` — Phase 1 of `REFERENCE_TRUST_FILTER_SOLUTION.md`: samples `SelfieSegmentation` mask confidence at each landmark. `maskMatchesImageSpace` checks mask/image aspect ratio first — the segmenter runs with `enableRawSizeMask: true`, so a coordinate-space mismatch is possible on an EXIF-rotated photo (the same class of issue the sixth-session `img.bakeOrientation()` fix addressed elsewhere) — and returns "signal unavailable" rather than mis-sampling on mismatch. `computeSubjectBoundingBox` (unchanged) feeds Phase 2 below.

#### `reference_photo_crop_redetect.dart` *(rewritten, twelfth session)*
`reconcileWithCrop` — Phase 2 of `REFERENCE_TRUST_FILTER_SOLUTION.md`. Crops to `computeSubjectBoundingBox`'s result, re-runs `PoseDetector` (now `PoseDetectionModel.accurate` — see `reference_image_analyzer.dart`'s entry above) on just the crop (temp JPEG written to `Directory.systemTemp`, deleted after use). **Rewritten this (twelfth) session — no longer recovery-only.** Previously this function only ever filled in landmarks the original detector was missing; a landmark the original detector reported was always kept, however implausible. Now every gated landmark goes through `_verifyLandmark`, which returns one of `LandmarkDecision.keep` / `.recover` / `.reject` / `.absent`:
- `original == null` → `.recover` if the crop detector observed it in-frame with likelihood ≥ `kMinLandmarkLikelihood`, else `.absent`.
- `original != null` → `.reject` only when mask confidence at the *original* landmark's own coordinates is below `kContradictionMaskConfidenceCeiling` (0.1) **and** the crop detector either didn't observe it (likelihood below `kContradictionCropLikelihoodCeiling`, 0.3) or placed it outside the crop's own bounds (checked in crop-local coordinates, before the shift back into original-image space) — two independent signals required to agree, so a merely-weak crop re-detection alone can't override a landmark the original pass and the mask both still support. Geometric suspicion (`originalGate.suspectIndices`) is captured per landmark (`LandmarkVerification.geometrySuspect`) and logged, but intentionally excluded from the reject condition — it's known to false-positive on genuinely bent limbs, and the goal is to reject hallucinated landmarks, not merely difficult ones.
- Otherwise `.keep`, using the original detector's own `RawLandmark`.

The final `verified` map (kept + recovered landmarks only; rejected/absent landmarks simply never enter it) is run back through `PoseLandmarkGate.fromRawLandmarks` and a fresh `sampleMaskTrust` pass, same as the eleventh session's merge step. `changedAnyLandmark` is now `true` whenever any landmark was recovered or rejected (previously only tracked confirmed recoveries). New per-landmark debug logging: `LANDMARK_VERIFY <name>: originalLikelihood=... cropLikelihood=... cropObserved=... cropOutOfFrame=... maskConfidence=... geometrySuspect=... decision=...`, plus the existing summary line now also lists `rejected=[...]` alongside `recovered=[...]`/`confirmedRecovered=[...]`. **Not yet device-verified** — reasoned through against a real captured log's numbers (a "red-shirt" reference photo, confirming `leftHip`/`rightHip`/`leftKnee`/`rightKnee`/`leftAnkle`/`rightAnkle` correctly reject while `rightElbow`'s strong original mask support correctly keeps it despite a weak crop re-detection), not yet re-run to confirm end-to-end.

**Bug found and fixed the (eleventh) session prior, via a real test screenshot, not just by inspection:** the post-crop trust gates (`cropGate`, `mergedGate`) were built via `PoseLandmarkGate.fromRawLandmarks(...)` with no `maskSignal` argument, silently defaulting to `MaskTrustSignal.none` (`bypassed: true`). Phase 2 was therefore recovering landmarks on likelihood + geometry alone — the two signals Phase 1 exists specifically because they're insufficient — which let it recover the exact hip→knee→ankle chain Phase 1's real mask check had just correctly rejected on the test screenshot. (Superseded in spirit by the twelfth session's broader rewrite above, which subsumes this fix.)

`CoachingPhraseModelService` — wraps Gemma 3 270M via `flutter_gemma`/`flutter_gemma_mediapipe`. `isReady` is `_model != null`, which only becomes true after `ensureInstalled()` completes. **The twelfth session's investigation is closed (thirteenth session) — the call site was in `ai_coaching_providers.dart` all along; see that entry and `README.md` §14.** This file itself was not the site of the actual bug.

**Bug found and fixed (earlier session):** `_ensurePluginInitialized()` called `FlutterGemma.initialize(...)` without awaiting it, then immediately proceeded to `install()` — a race condition where `install()`'s call into `ServiceRegistry.instance` could run before plugin registration actually finished, throwing `Bad state: FlutterGemma not initialized!`. Confirmed on-device: the smoke test failed with exactly that error, and the log showed `UnifiedModelManager initialized successfully` printing *after* the test had already failed — proof the async init was still running in the background. Fixed by making `_ensurePluginInitialized()` `async` and awaiting the `FlutterGemma.initialize(...)` call before `ensureInstalled()` proceeds to `install()`.

**Second bug found and fixed this (sixth) session, from a device crash log:** `ensureInstalled()` called `FlutterGemma.getActiveModel(maxTokens: 128)` — too low. A real coaching prompt from `_buildPrompt()` reached 185 tokens on its own, already over `maxTokens` before any output token was generated, which aborted the native LLM inference process (`JNI DETECTED ERROR IN APPLICATION`, `SIGABRT`) instead of failing gracefully — this crash happens below the Dart/FFI boundary, so it's uncatchable by the `try`/`catch` around `generate()` in `voice_providers.dart`. Fixed by raising `maxTokens` to `512`. `_buildPrompt()` itself is otherwise unchanged and still has no explicit length cap — see the related `LIMITATIONS_AND_ROADMAP.md` §3 item on hardening this further.

**M6 fix, thirteenth session (audit migration step 3).** Both previously-bare `catch` blocks now route through `ErrorReportingService.instance.report(...)` with a categorized `context` string. `ensureInstalled()`'s body (previously wrapped only in a bare `finally` resetting `_installing`, with no `catch` at all — exceptions propagated silently uncounted) now has a `catch (e, st)` that reports with `context: 'coaching_phrase_model_service: model initialization failure'` and rethrows, preserving the existing propagation behavior for callers. `generate()`'s `catch (_) { return null; }` now reports with `context: 'coaching_phrase_model_service: inference failure'` before returning `null` — external behavior unchanged, only diagnosability improved.

#### `llm_contract.dart` *(new, exists standalone — audit migration step 5)*
`LlmCoachingContract.fromDecision(CoachingDecision)` — builds a structured prompt contract: `attributeTopic` (human-readable label per `CoachingAttribute`), `allowedTopics`/`forbiddenTopics` (derived from a per-attribute keyword table, `kAttributeTopicKeywords` — every other attribute's keywords become this one's forbidden list), `buildPrompt()` (a tighter, contract-driven alternative to `coaching_phrase_model_service.dart`'s own `_buildPrompt`). **Not called from anywhere yet** — neither listener uses this file. #### `llm_output_validator.dart` *(new, exists standalone — audit migration step 5)*
`LlmOutputValidator.validate(generated, LlmCoachingContract)` → `LlmValidationResult` — checks word count (`maxWords = 16`), digit/technical-term presence, forbidden-topic mentions, missing the attribute's own required topic, direction-word consistency (via `action_plan.dart`'s `DirectionWordChecker`), and "mentions being an AI." **Not called from anywhere yet** — a Gemma-generated phrase is currently spoken exactly as generated, unvalidated, by both `voice_providers.dart` and `voice_providers_v2.dart`. #### `model_lifecycle.dart` *(new, exists standalone — audit migration step 6)*
`ModelLifecycleManager` — a real state machine (`ModelLifecycleState`: uninitialized/initializing/installing/loading/ready/generating/error/recovering) replacing `CoachingPhraseModelService`'s three independently-mutated booleans (`isReady`/`_installing`/`_generating`) with one owned state, plus capped exponential backoff (`retryBackoff`, default `[5s, 15s, 60s]`) that doesn't require an app restart to clear — explicitly designed as the automatic-recovery mechanism `coachingAiUnavailableProvider` still lacks. `ensureReady(service)` wraps `service.ensureInstalled()`; `generate(service, decision)` wraps `service.generate(decision)`. Both route errors through an injected `LifecycleErrorReporter` callback. **Not wired into `ai_coaching_providers.dart` yet** (audit migration step 7) — `_install()` still calls `service.ensureInstalled()` directly. See `LIMITATIONS_AND_ROADMAP.md` §5.

#### `voice_providers_v2.dart` *(new, thirteenth session — audit migration step 10)*
`coachingStateMachineProvider` (owns one `CoachingStateMachine` per listener lifetime) + `voiceDirectorListenerV2Provider` — a second, parallel listener alongside `voice_providers.dart`'s, gated behind `coachingV2SettingsProvider` (off by default; the whole `tick()` body no-ops if the flag is off). ## features/voice_director/domain *(new heading, thirteenth session)*

Six new files, all part of the architecture audit's delivered domain layer (migration steps 4–6, wired in by step 8 for the first two below; the remaining four are not yet wired into any live path — see `LIMITATIONS_AND_ROADMAP.md` §5).

#### `action_plan.dart`
`ActionControllability` enum (`subjectAction`/`cameraAction`/`environmentAction`/`lightingAction`/`compositionAction`/`doNotCoach`) + `kAttributeControllability` (a static lookup, one entry per `CoachingAttribute`) + `kExpectedVisualEffect`. `ActionPlan` — `phrase`/`decision`/`sourceLayer`/`confidence`/`controllability`, with `severity` as a getter (`decision.normalizedSeverity`, not a stored field). `typedef PriorityAction = ActionPlan;` exists as a migration aid but is **not relied upon anywhere in the active app as of this session** — see `priority_engine.dart`'s and `voice_providers.dart`'s entries for why that alias briefly caused a real compile error and was deliberately not kept as the long-term reference. `pickBest(candidates)` sorts by severity then confidence; `pickAcrossTiers(poseAndFace, composition, lighting, tierRotation)` is the real tier-selection logic now used by `reference_comparison_engine.dart`'s `evaluate()` — any tier whose best candidate is `moderate`/`strong` wins immediately in fixed order, otherwise the tiers round-robin via the caller-owned `tierRotation` counter. Also has `DirectionalContract`/`DirectionWordChecker` (used by `llm_output_validator.dart` to check a generated phrase's direction words against the decision's actual direction).

#### `root_cause_engine.dart`
`RootCauseCluster` enum (`torsoRotationOrLean`/`headOrientation`/`facialExpression`/`none`) + `kClusterMembers`/`kAttributeCluster`/`kClusterRepresentative` static tables. `RootCauseEngine.collapse(candidates)` groups same-cluster `ActionPlan`s and merges each group into one representative decision (fixed representative per cluster where specified — e.g. `bodyYaw` for torso rotation — else the highest-severity member), boosting `normalizedSeverity` to the cluster's max and combining confidence via `Confidence.minOf` across all members (a torso-rotation cluster is only as trustworthy as its least-confident contributing attribute). Singletons (attributes with no cluster) pass through unchanged. Used by `reference_comparison_engine.dart`'s `evaluate()`/`evaluateTiers()` on the `poseAndFace` tier only.

#### `coaching_eligibility.dart`
`IneligibilityReason` enum + `EligibilityResult` + `CoachingEligibility.evaluate(...)`/`evaluatePlan(plan, {...})` — a specific-reason gate (confidence floor via `core/confidence/confidence.dart`'s `ConfidenceFloors.eligibleToSpeak`, controllability vs. a `cameraFacingChannelEnabled` flag, subject-in-frame, detector-agreement, temporal persistence, cooldown) returning *why* a candidate was rejected, not just a bool. **Wired into `voice_providers_v2.dart`'s `CoachingStateMachine` this session, but three of its four non-confidence inputs are stubbed `true`** — see that file's entry and `LIMITATIONS_AND_ROADMAP.md` §5. Not used by the original (v1) listener at all.

#### `coaching_state_machine.dart`
`CoachingState` enum (`observe`/`verify`/`selectPriority`/`instruct`/`wait`/`reobserve`/`verifyImprovement`/`confirm`/`escalate`/`abandon`) + `SessionMemory` (per-attribute attempt/reversal counts, session-scoped suppression, post-resolution grace period) + `EligibilityContext` + `CoachingStateMachine` — a pull-based state machine (the caller drives it via `observe()`/`instructed()`/`reobserve()`/`next()` with fresh measurements each call, rather than owning any timer itself). Replaces the flat `Timer`/`lastDedupeKey`/`generationEpoch` trio `voice_providers.dart` still uses. **Wired into `voice_providers_v2.dart` this session** — see that entry for how the pull-based design is driven (off `subjectProfileProvider` frame updates, not a separate poll timer).

#### `correction_feedback.dart`
`CorrectionOutcome` enum (`improved`/`overshot`/`reversed`/`unchanged`/`unmeasurable`) + `CorrectionRecord` — `close({measuredValue, measurementConfident})` classifies the outcome by comparing pre/post measurement against `referenceTarget` (or `expectedDirection` if no target). A `null`/unconfident measurement always classifies as `unmeasurable` rather than guessing. **Used by `coaching_state_machine.dart`'s `reobserve()`**, which is in turn used by `voice_providers_v2.dart` — see that entry for how `null` measurements for `faceYaw`/`expression` (no scalar signal — see `reference_comparison_engine.dart`'s entry) are handled gracefully via this classification.

#### `adaptive_correction_model.dart`
`IntensityAdjustment` enum (`asAuthored`/`soften`/`strengthen`) + `ResponsivenessModel` — a per-attribute exponential moving average of "how far did they actually move per unit of instructed intensity" (`recordOutcome`, fed by `CorrectionRecord`s), meant to soften or strengthen which pre-authored phrase tier (mild/moderate/strong) to use for the *next* instruction on the same attribute via `adjustedBand()`. Deliberately does not invent new wording — only selects among tiers already authored in `reference_comparison_engine.dart`, so it introduces no new hallucination surface. `CoachingStateMachine` owns one instance per session and *does* call `recordOutcome()` automatically from inside `reobserve()` on every improved/overshot/reversed outcome, so responsiveness data is being collected. **But nothing calls `adjustmentFor()`/`adjustedBand()` anywhere** — not `coaching_state_machine.dart` itself, not `voice_providers_v2.dart`'s tick loop — so the collected data has no effect on phrase selection yet. Wiring that read-back in is a small, self-contained follow-up, not attempted this session.

## features/reference_photo/presentation/widgets

#### `reference_picker_sheet.dart`
**Changed again this (twelfth) session — the eleventh session's fix here was itself incomplete.** `ReferenceAnalysisPainter` no longer calls `PoseLandmarkGate.fromPoints(pose)`. That call, added last session to supposedly make the painter "draw exactly what the gate returns," actually built a **second, independent** gate from bare coordinates — no likelihood, no mask, `maskSignal` silently defaulted to `MaskTrustSignal.none` — and re-ran the full geometric suspicion heuristic against that impoverished data, sometimes disagreeing with the authoritative gate in `reference_image_analyzer.dart` about what's trusted. (This is the confirmed root cause of the `maskBypassed` mismatch between `ReferenceImageAnalyzer gate:` and `ReferenceAnalysisPainter gate:` log lines observed repeatedly across the eleventh and twelfth sessions.) Fixed by removing the second gate entirely: `paint()` now iterates `poseLandmarkPoints` directly via the shared `usablePointAt()` helper (`core/pose/landmark_gate.dart`) and draws a skeleton connection only when both its endpoints are non-null — no trust/suspect decision of any kind left in this file.

Previously (through the tenth session), this doc described the heuristic now living in `core/pose/landmark_gate.dart` as follows — kept here since the underlying logic itself is unchanged, only relocated (eleventh session) and no longer consulted by this file directly (twelfth session): not a flat 4x-length cutoff, but accumulated weighted "suspicion evidence" per landmark from four independent signals (segment length vs. a `_bodyUnit` scale derived from the median-then-largest-plausible candidate across several body measurements with outlier rejection; a symmetric left/right pair collapsing toward the same point; a large bilateral length mismatch between a mirrored limb pair; a limb crossing into the opposite body half beyond a margin, with a relief term so legitimately crossed arms don't false-positive), only hiding a landmark once evidence crosses a fixed threshold, with a safety valve that backs off entirely if more than 60% of present body landmarks would be flagged at once.

**Bug found and fixed this (tenth) session — `ToleranceSliders`.** The four sliders, labeled "Pose/Composition/Expression/Color strictness," read/wrote `ToleranceSettings`'s `*Tolerance` fields directly. Every threshold formula in `comparison_math.dart` treats a *higher* tolerance as a *larger, more forgiving* threshold — the opposite of what "strictness" implies, so dragging a slider down to make the app "less picky" actually made it stricter, and vice versa. Fixed: sliders now display/write `1.0 - tolerance.*`; `ToleranceSettings`'s own field semantics are unchanged everywhere else in the codebase — this is a UI-only inversion.
