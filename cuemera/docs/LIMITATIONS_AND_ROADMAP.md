# Known Limitations & Upgrade Roadmap

All P0 and P1 hygiene items are resolved. A sixth session fixed four additional device-confirmed bugs (front/back camera rotation, a native crash in Track 2, an EXIF-orientation bug, and an Android release-build failure) — see `README.md` §3a/§4/§6 for the account of each. **A seventh session started adding `sherpa_onnx` (VITS/Piper) as a second, primary TTS engine — this work is incomplete as of this writing** (asset wiring not finished, nothing device-verified yet); see `README.md` §8 and item 1 below.

## 1. Needs physical-device testing

- **Finish `sherpa_onnx` TTS asset wiring, then device-test the whole path.** `pubspec.yaml`'s `assets:` list still needs every `espeak-ng-data/` subdirectory added explicitly (Flutter doesn't bundle directories recursively) — get the real subdirectory list via `find assets/models/vits-en -type d` and fill it in. Once that's done, this is entirely unverified: confirm `SherpaTtsService.init()` actually reaches `isReady == true` on a real device (the asset-extraction step, reading `AssetManifest.json` and copying every matching file to a writable directory, has never been run), confirm generated audio actually plays through `audioplayers`, and confirm `AppTtsService`'s fallback to `flutter_tts` actually kicks in cleanly if any of that fails partway through a session (not just on first launch).
- **Re-confirm the front/back camera rotation fix.** `MlKitService.rotationFor()` was rewritten this session to apply the correct lens-direction-specific formula (previously the caller used a single, device-orientation-blind formula for both cameras — see `README.md` §3a). The original symptom (`shoulderAngle`/`faceAngle` reading `FAIL` on the front camera despite a matching pose) was only observed via a debug-overlay screenshot, not a repeatable test — re-run on a physical device with the front camera and confirm the debug overlay reads `OK` for a genuinely matched pose. Also worth checking: does the app lock portrait orientation? If not, test with the phone rotated too, since `deviceOrientation` now actually matters for the computed rotation in a way the old formula ignored entirely.
- **Test the Impeller-disable mitigation across more devices.** One device (model "7 ZS67") showed clearly worse frame pacing with Impeller (the default renderer) than with Skia (`--no-enable-impeller`) — matches known upstream issues, not app-specific. The recommended fix (add `<meta-data android:name="io.flutter.embedding.android.EnableImpeller" android:value="false" />` to `AndroidManifest.xml`) has **not been confirmed applied to the manifest yet** — check whether it's actually there, and if so, whether it resolves jank on other test devices too, since Impeller regressions are GPU/driver-specific and this device is only one data point.
- ~~**`CameraService.capture()`'s per-photo controller lifecycle needs a redesign decision.**~~ **Superseded.** `CameraService` was merged this session from two independently-opened `CameraController`s (one for the live ML-analysis stream, one for preview/capture) into a single shared controller, matching how CameraX is actually meant to be driven (Preview + ImageAnalysis + ImageCapture as one bound session). `capture()` now just stops/resumes that one controller's image stream around `takePicture()` rather than juggling separate controllers — there's no more per-photo controller setup/teardown to redesign. **Needs physical-device verification** (the design decision itself is now resolved, see above): confirm continuous autofocus now behaves correctly (this was the original symptom — an Oppo Reno 14 showed preview/capture visibly softer than the stock camera app and non-continuous-feeling AF, matching known CameraX behavior on devices reporting a `LIMITED` Camera2 hardware level), confirm the ML Kit overlay/coaching resumes normally after a capture (i.e. the internal stream-resume actually fires), confirm `switchLens()` still works including front-camera rotation correctness, and validate that `ResolutionPreset.high` (the preset now used for the merged controller, previously only used for preview) doesn't slow down ML Kit frame processing to an unacceptable degree — no resolution-negotiation code was added to compensate, since CameraX already handles this internally when multiple use cases share one session.
- **Measure the real wall-clock impact of `ReferenceImageAnalyzer.analyze()`'s concurrency.** Its five independent steps (pose, face, segmentation, decode, palette) now run via `Future.wait` instead of sequentially. Confirm on a physical device that this actually cuts latency — ML Kit's native platform-channel bindings may serialize these calls internally regardless of Dart-level concurrency, in which case the real-world win could be smaller than assumed.
- **Verify `_evaluateFaceRoll`'s left/right direction in `reference_comparison_engine.dart`.** The phrase direction is derived from ML Kit's documented `headEulerAngleZ` sign convention, gated behind a `_faceRollDirectionIsMirrored` flag (currently `false`). This hasn't been confirmed on a physical device — tilt your head to a known side and check which phrase fires; flip the flag if it's backward. Now that the `subject_profile.dart`/`tracking_engine.dart` fix means this evaluator actually runs in production, getting the direction right matters more than when it was previously dead code. **Same verification now also needed for the new `_evaluateFaceYaw`'s `_faceYawDirectionIsMirrored` flag** — turn your head to a known side and confirm the left/right phrase matches, flip the flag if backward.
- **Re-tune auto-capture thresholds after `AutoCaptureService`'s new gates.** `shouldCapture()` now also gates on `bodyRatio`/`mouthOpen`/`negativeSpace`/`symmetry` (previously coaching-only, no bearing on capture timing at all). This makes auto-capture strictly harder to trigger than before — confirm on a physical device that a real subject can still reasonably satisfy all gates at once within `minTrackingProgressForCapture`, and re-tune `ToleranceSettings`/`DetectionThresholds` if auto-capture now rarely or never fires.
- **Confirm `ReferenceComparisonEngine.evaluate()`'s tier-rotation fallthrough actually surfaces composition/lighting coaching in a live session.** Previously composition/lighting were never spoken as long as pose & face had any mild issue; the new round-robin (`_tierRotation`) is meant to fix that, but hasn't been confirmed on-device — run a real session with a deliberately-off reference (e.g. wrong background/lighting but otherwise fine pose) and confirm those cues actually get voiced in rotation, not just pose/face repeating.
- **Verify `_shoulderBalanceDirectionIsMirrored`/`_bodyYawDirectionIsMirrored` in `reference_comparison_engine.dart`, and sanity-check `bodyYawEstimate`'s z-depth derivation.** Both flags default to `false` and are unverified on a physical device, same as `_faceRollDirectionIsMirrored` above — nudge one shoulder to a known side / turn your torso to a known side and confirm the phrase names the correct side, flipping the flag if backward. `bodyYawEstimate` additionally relies on ML Kit's *experimental* shoulder z-depth (`atan2(rightShoulder.z - leftShoulder.z, dx)`), which Google's own docs call less accurate than x/y — before trusting the flag alone, run a few test poses (facing camera, then turned roughly 30°/60° each way) and confirm the raw value moves monotonically rather than reading noisy or backwards, since this is new math with no validated precedent elsewhere in this codebase. Only `ReferenceImageAnalyzer._analyzePose` computes `shoulderBalanceRatio`/`shoulderSpanRatio`/`bodyYawEstimate` so far — the live side (wherever `SubjectProfile` gets built from the camera pose stream, see `README.md` §2's data-flow diagram) still needs the same computation added before these three evaluators can fire outside a reference-photo-only test.

## 2. Needs test coverage / code audit

- **`reference_image_analyzer.dart`'s `analyze()` orchestration is still untested.** It constructs real `PoseDetector`/`FaceDetector`/`SelfieSegmenter` instances internally and calls their native `processImage()` directly — there's no seam to inject a fake, so exercising `analyze()` itself needs a physical device/platform channel, not a pure-Dart test. `face_analyzer_test.dart` now covers `face_analyzer.dart` fully (`Face`'s public constructor makes it directly testable), and `reference_image_analyzer_test.dart` covers the four pure pixel/mask helpers (`estimateNegativeSpace`/`estimateSymmetry`/`estimateBackgroundClutter`/`estimateBrightness`, made public + `@visibleForTesting` for exactly this purpose) — but the pose/face detection calls and the `bodyRatio`/`poseLandmarkPoints` landmark logic inside `_analyzePose`/`_analyzeFace` remain uncovered. If `analyze()` itself needs to be under test, it likely needs a constructor-injected detector seam first.
- **No unit tests yet for `_evaluateShoulderBalance`/`_evaluateShoulderSpan`/`_evaluateBodyYaw`** (eighth session, see `README.md` §9). Should mirror `reference_comparison_engine_test.dart`'s existing coverage for `_evaluateShoulderAngle`/`_evaluateFaceRoll` — null-field skip case, deviation-under-threshold no-fire case, mild/moderate/strong tier boundaries, and correct `direction` on both sides of the comparison for all three.

## 3. Needs a product decision

- **Wire `ErrorReportingService` to a real remote sink.** It currently only retains the last 200 reports in memory (`FlutterError.onError`, `PlatformDispatcher.instance.onError`, `runZonedGuarded`, and every previously-silent `catch` all route through it) — reports don't survive app restart and never leave the device. A `TODO(remote-sink)` marks the extension point; needs a service chosen (Firebase Crashlytics, Sentry, custom backend) and an account/API keys before this can be wired up.
- **`enableClassification: false` on the live `FaceDetectorOptions` contradicts what this project's docs previously assumed** (`README.md` used to say classification was enabled downstream of Track 1's flag). As it stands, `eyesOpen`/`expression` are `null` for two independent reasons — the detector-level config *and* `FaceAnalyzer.enableEyeAndExpressionSignals = false` — meaning flipping the Track 1 flag back to `true` in the future would silently do nothing, since classification is already off one layer up. Needs a decision: either enable classification to match Track 1's original intent (re-enabling the eventual re-enable path), or update the docs/intent to reflect that classification is meant to stay off and remove the now-redundant `enableEyeAndExpressionSignals` flag.
- **Harden `CoachingPhraseModelService._buildPrompt()` against future prompt-length growth.** `maxTokens` was raised 128 → 512 this session after a real prompt (185 tokens) crashed the native inference process (see `README.md` §4) — but there's still no explicit length cap on the prompt itself, so a longer `fallbackPhrase` or a new `CoachingAttribute` down the line could reproduce the same crash. Needs a decision on approach: a rough character-based heuristic cap (cheap, approximate) vs. an actual tokenizer-based count (accurate, adds a dependency) before this class of bug is considered closed rather than just pushed further out.
- **Type `voice_providers.dart`'s `emphasisFor()` parameter properly.** It's currently written with no type annotation on purpose (`emphasisFor(severityBand)`) because `coaching_decision.dart`'s actual `severityBand` return type wasn't available when this was written — the string-matched `.name` call works if it's a plain Dart enum, but this should be tightened to a real type once that file is confirmed, both for compile-time safety and to catch a future rename of the enum's values.

## 4. Model-driven upgrade — the core "complete product" gap

**Track 2 (Gemma 3 270M coaching phrases) is now active.** Phases 0–2 are code-complete and device-verified: the integration smoke test passed on a physical device (all 5 sample `CoachingDecision`s installed and generated successfully), and a Settings toggle ("AI Coaching Phrases") now controls activation end-to-end — persisted via `MemoryService`, gating both `ensureInstalled()` and the live coaching path in `voiceDirectorListenerProvider`. See `README.md` §4 for the full account, including three bugs found and fixed getting here (an unawaited `FlutterGemma.initialize()` race condition, an `assert`-based crash when `HF_TOKEN` is unset, and — found via a real device crash log this session — a native `SIGABRT` when a coaching prompt exceeded the too-low `maxTokens: 128`, fixed by raising it to `512`; see item 3 above for the follow-up hardening this still needs).

**Remaining, in order:**
1. **Capture a full Phase 3 dataset.** Only one of the 5 sample decisions' latency was captured in this session's log (`hue`/strong: 2200ms). Re-run the smoke test and save the complete output — need all 5 latencies, plus real-device usage during an actual shoot, to judge whether `gemma-3-270m-it-q8` is the right size/quantization and whether phrasing is actually natural-sounding.
2. **Getting the Hugging Face gated-model access right the first time is fiddly** — worth a one-line note in onboarding docs for future contributors: having a valid `HF_TOKEN` isn't sufficient on its own; the account behind that token must separately visit `litert-community/gemma-3-270m-it` on huggingface.co and accept the Gemma license, or every download attempt fails with an HTTP 401.
3. Once (1) is done and the app's seen real use: judge phrase-quality/naturalness, and revisit whether the ~304MB download size is worth it for a 270M model vs. a smaller quantization if one becomes available.

**Toolchain note (this session):** getting `flutter_gemma`/`flutter_gemma_mediapipe` building on Android required bumping AGP (`8.7.3` → `8.11.1`), Gradle (`8.12` → `8.14.3`), Kotlin (`2.1.0` → `2.2.20`), and NDK (`27.0.12077973` → `28.2.13676358`, specifically required by `integration_test`). All are now current — see `README.md`'s Toolchain section. Worth knowing if this project sits untouched for a while and these plugins get further updated: the AAR-metadata-vs-AGP-version failure mode (`checkDebugAarMetadata`) is likely to recur with future dependency bumps and is a quick diagnosis (`./gradlew assembleDebug --stacktrace` — the real error is always further up than Flutter's wrapped exit-code message suggests).

**Toolchain note (sixth session) — resolved:** the above toolchain bumps got the app compiling, but `flutter build apk --release` separately failed at `:app:minifyReleaseWithR8` with two missing MediaPipe profiling classes. Root cause: `android/app/build.gradle.kts`'s `release` block had no `proguardFiles(...)` call at all, so ProGuard/R8 rules were never applied regardless of what existed in `proguard-rules.pro`. Fixed by adding `proguardFiles(getDefaultProguardFile("proguard-android-optimize.txt"), "proguard-rules.pro")` and creating `proguard-rules.pro` with the two `-dontwarn` lines Gradle's generated `missing_rules.txt` specified. A release APK now builds (~230MB — `--split-per-abi` would shrink this considerably for real distribution, since the current build bundles all ABIs into one universal APK).

**Toolchain note (seventh session) — resolved, but see item 1 above for what's still incomplete:** while wiring up `sherpa_onnx`, `pubspec.yaml` was found with two structural bugs unrelated to sherpa_onnx itself but blocking it entirely: a top-level `assets:` key (Flutter silently ignores `assets:` unless it's nested under `flutter:` — meaning *no* assets, including the pre-existing `assets/images/`, were ever actually being bundled), and `flutter_launcher_icons.image_path` had `assets/models/vits-en/` mistakenly appended to what should be a single icon-file path. Both fixed. Separately noticed but **not fixed**: `environment.sdk: ^3.8.1` in this same file doesn't match the `^3.12.0` this doc's own Toolchain section above says was bumped to for Track 2 — worth resolving which one is actually true on the current dev machine before it causes confusion.
