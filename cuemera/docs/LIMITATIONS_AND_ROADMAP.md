# Known Limitations, Technical Debt & Upgrade Roadmap

Findings were originally verified against the actual code in the initial session (all 53 `.dart` files + `pubspec.yaml`). **This version reflects two follow-up sessions**: the first fixed every P0 item but one, every P1 item, and nearly all of the hygiene backlog; the second closed out the remaining P0 item and 8 of the 9 "remaining" roadmap items below (test suite, crash/error reporting foundation, Hive schema versioning, gallery-save visibility, ML Kit fallback, `atan`/`atan2`, `Shot` provenance, and an interim step on the model-driven phrase system). **A third, live-debugging session** (triggered by real on-device testing, not a code audit) found and fixed three issues that weren't part of the original scan:
- **Front-camera rotation bug (new, high-impact):** `camera_screen.dart` computed ML Kit's `InputImageRotation` with the same formula for front and back cameras. Front sensors need a different compensation (`(360 - sensorOrientation) % 360`, not `sensorOrientation` directly) — without it, every live pose/face landmark on the front (selfie) camera was computed in the wrong orientation, causing shoulder-angle coaching and `trackingProgress`/auto-capture to appear persistently wrong even when correctly posed. The reference-photo pipeline (a static file, no camera involved) was unaffected — this matches the "reference looks right, live tracking is always off" symptom exactly. **This likely explains why auto-capture appeared non-functional even after the P0/P1 fixes in the second session** — `trackingProgress` could never reach its 0.9 threshold with systematically wrong angles feeding it.
- **TTS silently dead (new):** `TtsService.init()` was never called anywhere in the codebase — `ttsServiceProvider` only constructed the service and returned it, so `_ready` stayed `false` forever and every `speak()` call silently no-op'd. Root cause of "no voice coaching at all." Fixed by calling `init()` from the provider.
- **Pose-skeleton preview outlier (new, cosmetic):** the reference-photo picker's pose overlay could draw an implausible line when a photo was framed to cut off before the knee/wrist — ML Kit sometimes reports a confident-but-wildly-wrong position for landmarks outside the frame. Fixed with a segment-length outlier check in `ReferenceAnalysisPainter`. Related, **not yet fixed**: `bodyRatio` in `reference_image_analyzer.dart` computes from the same class of landmark without going through this filter, so scoring/tracking accuracy for partial-body reference photos may still be affected — flagged below.
- **Product decision applied, not a bug:** `TargetZoneOverlay` was removed from `camera_screen.dart` at the user's request (it visually implied the subject had to fit inside a fixed box, which the underlying comparison never actually required).

Only genuinely outstanding items remain in the sections below.

## 4. Known Limitations & Technical Debt (still outstanding)

### P1 — real gap found during live testing, not yet addressed

- **`bodyRatio` may be skewed for partial-body reference photos.** `reference_image_analyzer.dart` computes `bodyRatio` directly from raw `nose`/`leftHip`/`leftAnkle` landmarks, without applying the same `_minLandmarkLikelihood` confidence filter used for `poseLandmarkPoints` (the one the picker's preview draws from). If `leftAnkle` is outside the frame (e.g. a half-body reference photo — the app's own `half_body` shot type implies this is a real, expected use case, not an edge case), ML Kit can still report a confident-but-wrong position for it, silently skewing `bodyRatio` and anything that depends on it (scoring, live tracking comparison). Found via the pose-skeleton preview bug above; not yet fixed since the reported symptom was scoped to the preview only.

### P2 — polish / hygiene (not yet addressed)

- `LightAnalyzer._estimateColorTone`'s `planes[1]=U, planes[2]=V` assumption is still unverified against the real camera stream's plane layout — this requires testing on a physical device (log `planes[1]`/`planes[2]` averages against a known pure-red/pure-blue target and compare to the derived hue/warmth), which is out of scope for a code-only session.
- `CameraService.capture()` still spins up a brand-new `ResolutionPreset.max` `CameraController` for every single photo (in addition to the two already-running controllers), then disposes it. Per-capture latency is now **instrumented** (`lastCaptureControllerSetupLatency`/`lastCaptureShutterLatency`/`lastCaptureControllerTeardownLatency`, logged via `debugPrint` on every capture), but no architectural change (e.g. reusing an existing controller at the cost of capture resolution) has been made — that's a product trade-off decision pending real numbers from the instrumentation.
- `reference_image_analyzer.dart`, `reference_image_analyzer.dart`'s pose/face/segmentation detector calls, and image decode/palette generation all currently run **sequentially** even though none depends on another's result — running them concurrently (e.g. via `Future.wait`) would reduce the "pick a reference photo" wait time in both debug and release builds, unlike JIT-vs-AOT compilation differences which only affect the pure-Dart pixel-sampling loops, not the ML Kit platform-channel calls themselves. Flagged during a user question about why photo-picking felt slow; not yet implemented.

## 3. Gap Analysis Against a "Complete Product" Standard (still applies)

**Where is the app relying on placeholder/self-authored logic instead of a trained model or robust system?**
The voice-coaching layer is still rule-based, not model-driven, though less flatly so than before: `reference_comparison_engine.dart`'s `_evaluate*` methods now select from severity-tiered phrase banks (mild/moderate/strong per attribute) instead of one fixed literal per direction — a real improvement in variety and specificity, but still hand-authored strings selected by threshold/sign logic, not a learned model. `score_calculator.dart`'s `_expressionScore` fallback (no-reference case) is still a literal if/else ladder. The live and reference-photo expression classifiers remain unified in one shared function (`expression_classifier.dart`) but are still a hand-tuned probability-threshold ladder. There is no LLM, no fine-tuned classifier, and no prompt/response pipeline anywhere in the codebase.

**What would replacing this with an actual trained/fine-tuned model require?**
- *Data:* paired (live-frame pose+face+scene features, reference-photo features, human-rated "what should the coach say / how close is this") examples — realistically requires either a labeling pass over recorded sessions or synthetic generation from the existing `ComparisonMath` deviations as weak labels to bootstrap.
- *Model:* two candidate directions — (a) a small classifier/ranker over the existing numeric feature vector to pick *which* attribute to correct and *how urgently*, replacing `ReferenceComparisonEngine`'s hand-ranked severity; and (b) an on-device GenAI call (Gemini Nano via ML Kit's GenAI Prompt API on Android; Apple's Foundation Models framework on iOS, which now accepts multimodal image input) that takes the structured deviation summary and generates the coaching phrase in natural language. Both platforms' on-device models have real availability limits (device/AICore requirements on Android; regional restrictions — e.g. EU, mainland China — and hardware requirements on iOS), so any integration needs the current rule-based phrase bank kept as the fallback path, not replaced by it.
- *Evaluation:* human-rated coaching-phrase quality/appropriateness on held-out sessions; agreement rate between the model's "worst attribute" pick and a human's; expression-classification accuracy against a labeled validation set.
- *Deployment:* on-device (Gemini Nano / Foundation Models) is the closer fit than a hosted API call per frame, given the 80 ms per-frame throttle already in place; a hosted call is more plausible for the reference-photo one-shot analysis path, where latency budget is looser.

**Which modules are production-ready, prototype-quality, or missing?**
- *Production-ready as-is:* `comparison_math.dart`, `app_theme.dart`/`app_colors.dart`/`app_typography.dart`/`app_spacing.dart`, `tolerance_settings.dart`, `detection_thresholds.dart`, `scene_profile.dart`/`subject_profile.dart`, `shot.dart` (persistence + provenance), `focus_ring.dart`/`phrase_chip.dart`/`score_badge.dart`/`primary_button.dart`, `expression_classifier.dart`, `score_calculator.dart` (story score fixed), `error_reporting_service.dart` (as a local foundation).
- *Prototype-quality (works, but with the gaps above):* the voice-director phrase system (tiered but still rule-based), the album diversity feature (reachable, suggestions still a simple least-represented-type heuristic), reference-photo analysis (functionally complete but the `_estimateColorTone` plane-layout assumption remains unverified), `CameraService.capture()`'s per-photo controller lifecycle (now measured, not yet redesigned).
- *Missing entirely:* a real remote crash/error-reporting sink (a local in-memory foundation exists — see below); localization; any model-driven text generation; CI/build config beyond `pubspec.yaml`.

**Security, privacy, or reliability gaps?**
- No rate limiting or backpressure beyond the fixed 80 ms per-frame throttle and the `_busy` re-entrancy guard in `MlKitService` — both local performance safeguards, not the kind of gap that applies to a fully on-device, no-backend app.
- No authentication/authorization surface exists because there's no backend or account system in this codebase.
- Photos are saved directly to the public gallery on every capture (`Gal.putImage`) with no user confirmation step and no way to review before it lands in their camera roll. Gallery-save failures are now surfaced to the user (a snackbar via `gallerySaveWarningProvider`) and logged (`ErrorReportingService`) — previously both silent.
- `ErrorReportingService` now centralizes crash/error capture (`FlutterError.onError`, `PlatformDispatcher.instance.onError`, `runZonedGuarded`, plus every previously-silent `catch` in `reference_image_analyzer.dart`, `album_providers.dart`, and `camera_service.dart`) and retains the last 200 reports in memory. It is **not yet a remote sink** — reports are lost on app restart and never leave the device. Wiring a real service (Firebase Crashlytics, Sentry, or similar) is a deliberately-deferred product decision (needs an account/API keys), with a marked extension point (`TODO(remote-sink)`) in the service itself.
- `MlKitService` now flags itself unavailable after 5 consecutive per-frame failures (typically a failed on-device model download/initialization) and the UI shows a persistent banner — previously a failure here degraded silently with no user-facing explanation.

## 5. Upgrade Roadmap (remaining)

**Correctness (new, found during live testing):**
1. Fix `bodyRatio`'s computation in `reference_image_analyzer.dart` to use the same `_minLandmarkLikelihood`-filtered landmarks as `poseLandmarkPoints`, instead of raw `nose`/`leftHip`/`leftAnkle` — closes the same out-of-frame-landmark issue the pose-skeleton preview fix addressed, but for the actual scoring/tracking data path this time.

**Hygiene / cleanup (remaining):**
2. Verify the `planes[1]=U, planes[2]=V` assumption in `LightAnalyzer._estimateColorTone` against the actual camera stream's plane layout on target devices (requires physical-device testing, not a code change).
3. Decide whether to redesign `CameraService.capture()`'s per-photo controller lifecycle now that its latency is instrumented — reusing an existing controller would need to trade off against capture resolution.
4. Run `ReferenceImageAnalyzer.analyze()`'s independent steps (pose/face/segmentation detection, image decode, palette generation) concurrently via `Future.wait` instead of sequentially — none depends on another's result, and this would cut real wall-clock latency in both debug and release builds (unlike the JIT-vs-AOT speedup, which only helps the pure-Dart pixel-sampling loops).

**Monitoring (remaining):**
5. Wire `ErrorReportingService` to a real remote sink (Firebase Crashlytics, Sentry, or a custom backend) once one is chosen, so reports survive app restarts and are visible without a connected device.

**Model-driven upgrade (the core "complete product" gap):**
6. Replace `ReferenceComparisonEngine`'s severity-tiered-but-still-hardcoded phrase bank with an on-device GenAI call (Gemini Nano / ML Kit GenAI Prompt API on Android, Apple Foundation Models on iOS) for phrase generation, keeping `ComparisonMath`'s attribute/severity selection as the reliable rule-based layer underneath, and keeping the current phrase bank as the fallback for unsupported devices/regions. Requires native (Kotlin/Swift) integration work beyond pure Dart.
7. Fold the unified expression classifier into that same modeling effort rather than hand-tuning its thresholds further.
8. Scope a Quality Engine (aesthetic scoring beyond `ComparisonMath`'s geometric comparison) — no ready-made on-device model exists for this; realistic path is a NIMA-style small CNN (MobileNet/Inception backbone), fine-tuned and exported to LiteRT (TFLite's current name). Needs a labeled dataset (bootstrap from a public aesthetic-scoring dataset, fine-tune on real app data) before any model work starts.
