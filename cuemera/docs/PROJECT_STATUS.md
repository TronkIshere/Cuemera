# 1. Overview

Cuemera is an AI fashion photographer app built in Flutter. Its core philosophy is to direct the user like a real photographer would — giving live, spoken and visual cues — rather than asking the user to copy a static reference pose from a menu of categories. The system watches the user through the phone's camera in real time, understands their body, face, and the scene around them, compares it against a **user-supplied reference photo**, and produces a single, prioritized, real-time instruction at any given moment, then automatically (or manually) captures the shot when everything aligns, scores it editorially, and organizes it into an album that tracks shot diversity across a session.

The current architecture approach is 100% on-device edge AI in Flutter: camera capture (`camera`), pose/face/segmentation analysis (`google_mlkit_*` packages), local smoothing/decision logic in pure Dart, local persistence via Hive, and text-to-speech via `flutter_tts`. State is managed with Riverpod throughout. An optional Java/Spring backend has been discussed as a future layer but has not been started — everything today runs entirely on-device.

The app's entry navigation: `goal_selection_screen.dart` is not a goal-picker grid — it is the app's minimal home screen (Shoot / Album / Settings). The home screen's card widget lives in its own file (`goal_card.dart`, public `EditorialMenuCard`) and went through several rounds of layout/performance iteration (bento layout tried and reverted, ghost page-number tried and replaced with an outline-icon watermark, BackdropFilter/shadow performance fix).

## Reference-photo migration — COMPLETE

Instead of picking a category like "LinkedIn" or "Editorial," the user picks a reference photo and sets tolerance sliders (pose/composition/expression/color strictness); the app directs and scores the live shot by comparing it against that reference.

# 3. Data Flow (current, post-migration)

1. **Reference selection:** User taps the reference-photo icon in `CameraTopNavBar` → `ReferencePickerSheet` opens → user picks an image via `image_picker` → `selectedReferenceImagePathProvider` updates → `referenceProfileProvider` (a `FutureProvider<ReferenceProfile?>`) re-runs `ReferenceImageAnalyzer.analyze()` on the new path → user adjusts 4 tolerance sliders, each writing to `toleranceSettingsProvider`.
2. **Live sensing:** Camera image stream → `PoseAnalyzer`/`FaceAnalyzer`/`LightAnalyzer` extract raw `SubjectProfile`/`SceneProfile` → `TrackingEngine` applies EMA smoothing + debounce → smoothed profiles land in `subjectProfileProvider`/`sceneProfileProvider`.
3. **Direction:** `nextActionProvider` watches subject/scene/reference/tolerance → `ReferenceComparisonEngine.evaluate()` ranks the worst-deviating attribute → `voiceDirectorListenerProvider` debounces and speaks the resulting phrase via `TtsService`.
4. **Scoring:** `currentScoreProvider` watches the same inputs → `calculateReferenceScore()` produces a live `EditorialScore` for on-screen display.
5. **Auto-capture:** `shouldCaptureProvider` watches subject/scene/reference/tolerance/trackingProgress → `AutoCaptureService.shouldCapture()` gates on eyes-open, brightness, shoulder/face angle match (via `ComparisonMath`), background clutter, `trackingProgress >= 0.9`, and a 1500ms cooldown → `autoCaptureProvider` listener triggers `AutoCaptureService.triggerCapture()` + `buildShotFromCapture()` → result lands in `capturedShotProvider` → `camera_screen.dart` adds it to `albumStateProvider`.
6. **Manual capture:** `PrimaryButton` in `camera_screen.dart` calls `_performCapture()` directly — takes the photo via `CameraService.capture()` (max-res controller, also triggers Gallery save), reads reference/tolerance directly, builds the shot the same way, adds to album.
7. **Album:** `AlbumState` tracks all shots in memory, computes diversity score and next-suggested-shot-type across 5 shot types; delete removes both the in-memory entry and the on-disk file.

# 4. Known Gaps (apply regardless of migration — all still open)

- `dominantHue`/`warmthScore` on `ReferenceProfile` are permanently unused in live comparison until `SceneProfile` gains a live color-analysis field.
- `bodyRatio` never produces a directional instruction, only a neutral fallback — by design, not a bug to fix later without first deciding what the ratio should mean.
- The visible `EditorialScore` breakdown does not include a pose category even though pose similarity gates capture — a real UX inconsistency, not yet resolved either way.
- `NSPhotoLibraryUsageDescription` was never added to iOS `Info.plist` despite `image_picker` being used by `reference_picker_sheet.dart` — gallery picking will likely crash/fail on iOS until this is added.
- `FocusRing`'s fade-out is non-functional (`AnimatedOpacity` hardcoded to `opacity: 1.0`) — minor cosmetic polish.
- `AlbumState` is not persisted to Hive — restart clears the in-memory album (file-on-disk gallery copies persist, but the in-app album list does not).
- Album image quality/smoothness issue: captures look sharp when taken but appear blurry/less smooth in the Album grid/detail view — separate from the now-fixed live-preview blur. Needs `cacheWidth`/`cacheHeight` hints or a thumbnail-generation step in `album_screen.dart`.
- The 3 top-navbar icon buttons: reference-photo picker and flip-camera are wired and functional; adjustments/settings and mode-selector remain stubs with no defined target behavior.
- `goalSelectionTitle`/`goalSelectionSubtitle` strings in `app_strings.dart` are dead, not yet removed.
- `MemoryService` has no read-side consumer — implemented but unused; wiring personalization into `reference_comparison_engine.dart` is the natural next step now that the migration is complete.
- No real-device testing has been performed yet — FPS, battery drain, permission flow behavior, and `LightAnalyzer`/`ReferenceImageAnalyzer` heuristics are all unvalidated on physical hardware.
